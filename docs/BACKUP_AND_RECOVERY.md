# 备份与恢复方案

## 1. 备份目标

采用 3-2-1 原则：至少 3 份副本、2 种介质、1 份异地。ChatGPT 对话、浏览器 localStorage 和单台电脑都不算可靠备份。

## 2. 分层备份

### 代码和结构化题库

- 主副本：受保护的 GitHub 仓库；
- 第二副本：每周生成一次 Git bundle；
- 异地副本：另一云盘/对象存储或加密移动硬盘；
- 所有正式变化通过提交和 PR 留痕。

### 原始 PDF、音频和图片

- 不只依赖 GitHub；
- 存在启用版本管理的对象存储；
- 保留原始文件、处理后文件和来源清单；
- 每个文件保存 SHA-256 校验值；
- 授权文件和采购凭证与素材同级备份，但权限分开。

### 用户数据（上线后）

- 数据库每日自动备份；
- 建议保留：每日 7–14 天、每周 8 周、每月 12 个月；
- 对象存储开启版本控制和误删保护；
- 备份加密，访问权限最小化；
- 每季度做一次从空环境恢复演练。

### 配置和密钥

- 只保存配置模板，不将真实密钥提交到 Git；
- 真实密钥进入云端 Secret Manager 或部署平台密钥库；
- 生产、测试、开发使用不同密钥；
- 离岗/交接时立即轮换权限。

## 3. 当前项目立即执行

每次重要里程碑：

1. 确认所有源代码和题库已提交；
2. 推送到 GitHub；
3. 执行 `npm run backup -- /path/to/backup-root`；
4. 将生成的 Git bundle、工作树压缩包和 SHA-256 清单复制到异地位置；
5. 记录日期、提交 SHA、文件大小和保管人；
6. 抽查压缩包并至少每季度实际恢复一次。

备份脚本默认拒绝把输出写进项目目录，以免形成递归备份。备份可能超过 1GB，目标磁盘需预留充足空间。

## 4. 恢复

从 GitHub：克隆仓库、检出指定提交、恢复外部媒体、安装依赖，执行审计和构建，再对照清单核验 SHA-256。

从 Git bundle：

```bash
git clone mars-cambridge-YYYYMMDD-HHMMSS.bundle mars-cambridge-restored
```

再解压同时间戳的工作树压缩包，把媒体和未跟踪但需要保留的文件恢复到对应目录。

## 5. 责任

- 项目负责人：确认里程碑备份和异地副本；
- 开发者：提交、推送、不得把密钥放入仓库；
- 内容负责人：维护来源与授权清单；
- 上线后运维负责人：数据库备份、监控和恢复演练。
